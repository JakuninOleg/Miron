# Локальная база MIRON

Первая физическая схема реализована на PostgreSQL + Drizzle. Единственный ID аккаунта — UUID `users.id` Better Auth; параллельной системы сессий нет. Миграции находятся в `drizzle/`, схема — `src/server/db/schema.ts`.

11 октября применена `0011_old_mauler.sql`: в `profiles` добавлены выбранные интересы, operation ID и hash неизменяемого запроса завершения знакомства. `onboarding_completed` остаётся серверным признаком маршрутизации; повтор просмотра не сбрасывает его и не пересоздаёт `ai_trials`.

## Запуск

Из корня проекта:

```powershell
npm run db:local
npm run db:migrate
npm run db:seed
npm run dev
```

Локальный PostgreSQL использует отдельный кластер в `.local/postgres` и порт `55432`. `DATABASE_URL` берётся из игнорируемого `.env.local`; пароль и auth secret нельзя переносить в исходники. Скрипты миграции и seed загружают этот файл через `process.loadEnvFile`. Если используется другая база, сначала проверьте назначение `DATABASE_URL`.

Повтор миграции не применяет уже записанные версии. Повтор seed сохраняет существующие карточки и не меняет их статус. Seed отключён при `NODE_ENV=production`.

```powershell
npm run db:stop
```

Команда останавливает только локальный кластер проекта. Системная служба PostgreSQL не требуется.

## Что сохраняется

- Better Auth: аккаунты, сессии, провайдеры, verification и серверный rate limit.
- Профиль, дни занятий, локальное время напоминаний, персонаж, тема, подтверждение совершеннолетия; основной профиль инвентаря и количество ресурсов.
- Канонические упражнения, варианты, редакционные revision, нормализованные обязательные ресурсы, записи медиа и демонстрационные шаблоны.
- План, занятие, закреплённые revision карточек, копия текста, метрика, снимок места/времени/ресурсов, выполненные подходы, команды и XP ledger.
- Одна проба на аккаунт: 168 часов и 100 ответов. Резервы ответа отделены от фактического использования.

Оборудование, опоры и пространство не выводятся из слова «зал» или «дом». Одна гантель не считается парой. Ресурс, требующий подтверждённой устойчивости, недоступен без соответствующего факта. Текущий простой UI сохраняет количество; подтверждение опоры через него ещё не реализовано, поэтому такой подбор закрыт.

Личные дочерние строки используют составные FK владельца и родителя. Чужой `workoutId` не даёт доступа к карточке и не позволяет прикрепить подход к чужому занятию. Все приватные API проверяют серверную сессию и возвращают `Cache-Control: no-store`. Тела команд ограничены по размеру и проходят Zod-проверку; browser mutation также проверяет Origin.

`record_set`, `next_exercise`, `finish` принимают `operationId` и ожидаемую revision. В одной транзакции сервер блокирует аккаунт/занятие, проверяет revision, сохраняет результат и увеличивает revision. Повтор возвращает прежний `CommandAck`; повтор ID с другими параметрами отклоняется. XP вычисляет сервер: завершение даёт 50 XP, уникальное событие исключает повтор. Снимки уже созданного занятия не меняются при редактировании инвентаря.

Профиль сохраняется атомарно под блокировкой строки. Его внутренний revision уже есть, однако UI-контракт пока не отправляет ожидаемую revision: два последовательных сохранения профиля используют последнее пришедшее значение. Для тренировочных команд конфликт двух устройств возвращает `409`.

## Редакционный каталог

Все **300 карточек вариантов остаются `draft`**. Это инвентарь редакции, а не экспертно подтверждённая программа. Публичный selector требует `published` вариант, `published` revision, явный `standard_review` и согласованный ненавыковый `skillDemand` с `requiresPriorSkill=false`. Известные настоящие навыковые движения, неизвестный допуск и противоречивые метаданные закрыты. После seed он пуст. Публикация и реестр экспертных/медийных прав ещё не имеют редакторского интерфейса.

Миграция `0004` добавляет версии графов навыков, узлы с точными ревизиями карточек и связи между узлами одной версии. После semantic QA активны семь графов revision 2 (59 узлов, 59 связей). Прежние 14 revision 1 (98 узлов, 89 связей) сохранены как история; физически всего 21 ревизия, 157 узлов, 148 связей. Всё pending expert review. Новая SQL-миграция не понадобилась: уточнение хранится в существующем JSONB и новой версии графов. `npm run catalog:qa` проверяет данные до импорта. Seed не обновляет утверждённый граф или черновик упражнения, закреплённый таким графом, и не дописывает шаги в недемонстрационный шаблон.

Миграция `0002` добавляет `variant_revisions.editorial`, справочник 18 мышечных групп и связь мышц с конкретной ревизией/ролью. `0003` разрешает отдельный `workout_park` в профиле и наборе инвентаря; `outdoor` сохраняется. Seed объединяет два v1 JSON, V2-overlay и два расширения, проверяет сохранность всех прежних ID/семейств/метрик, меняет только редактируемые draft. Повторный импорт проверен на локальной БД: 300 ревизий, 1055 мышечных связей, все 300 существующих UUID, исторические графы и хеши снимков занятий сохранены. Детали и ограничения: [каталог](../data/catalog/README.md).

Четыре шаблона `demo-*` предназначены для локальной проверки сохранения данных. Сервер создаёт по ним занятие только при `ENABLE_DEMO_WORKOUTS=true` и `NODE_ENV != production`. Production отклоняет такой шаблон даже при включённом флаге. По умолчанию реальных опубликованных шаблонов нет. Демонстрационные инструкции прямо отмечают отсутствие экспертной проверки; рекомендации для реальных занятий не выдаются.

Условия CSV нормализованы как обязательный AND-набор. Редакционные категории поверхности сведены к явным `floor` / `clear_space` для демонстрации; эти поля не доказывают точные габариты. До публикации реальных программ нужны методическая проверка, точные требования, допустимость для уровня/шаблона и поддержка OR-альтернатив при необходимости. Персонажные изображения в этой схеме пока не связаны с карточками.

## Проба и AI

`initializeAccount` создаёт профиль и пробу с `ON CONFLICT DO NOTHING`. Signup hook вызывает его после регистрации; `GET /api/profile` восстанавливает отсутствующую запись без продления существующей пробы. Привязка/повтор входа не меняют её даты.

Будущий серверный AI gateway вызывает `reserveAiReply(userId, operationId)`, затем `settleAiReply(userId, reservationId, success)`. Блокировка строки пробы сериализует конкурентные резервы. `used + reserved <= reply_limit` защищено также CHECK. Неиспользованные резервы имеют срок пять минут и освобождаются при следующем запросе; повтор settlement не списывает квоту дважды. При `replayed=true` gateway не должен повторять вызов провайдера; полный ответ провайдера потребует отдельного журнала сообщений/результатов перед подключением Qwen.

Сейчас Qwen не подключён, локальные подготовленные ответы не расходуют пробу. Подписок, платежей, worker/outbox и push delivery в этой физической схеме нет.

## Проверки

```powershell
npm test
$env:RUN_DB_TESTS='true'
npx vitest run src/server/domain/database.integration.test.ts
```

Интеграционный тест допускает только loopback базу. Создаёт два аккаунта с уникальными UUID и удаляет именно их после проверки. Каталожный seed остаётся. Проверены реальные PostgreSQL-транзакции: tenant ownership и composite FK, неизменность снимка после изменения профиля, восемь конкурентных повторов одной команды, однократные XP за завершение, повторная инициализация пробы и 130 конкурентных резервов с ровно 100 принятыми. Unit-тесты проверяют количество ресурсов, неизвестное подтверждение опоры, конфликт operation ID, границу срока пробы и отсутствие клиентского права назначать XP.

Миграции успешно применены к локальному PostgreSQL 18.4. Восстановление из резервной копии и работа под эксплуатационной нагрузкой ещё не проверены. Эта реализация не утверждает production readiness.

Документация реализации: [транзакции Drizzle](https://orm.drizzle.team/docs/transactions), [PostgreSQL + Drizzle](https://orm.drizzle.team/docs/get-started/postgresql-new).
