# MIRON: задачи первой реализации

6 октября 2026. Общая очередь разработки из [дорожной карты](miron-roadmap.md). Первая локальная вертикаль уже реализована; актуальный состав — [README](../README.md), физическая схема — [database-setup.md](database-setup.md), доказательства — [verification.md](verification.md). Ниже исходный расширенный checklist для будущих этапов; его пункты не являются отчётом о завершённой работе. SMS исключён; дальнейший auth spike относится к живому Яндекс/VK.

## 0. Контракты до scaffold

- [ ] Утвердить первую группу таблиц и команд SessionEngine.
- [ ] Сопоставить 72 draft-кандидата с resource vocabulary; выбрать 12 пилотных вариантов.
- [ ] Проверить матрицу первого пилота: программа без инвентаря и программа с одной гантелью без обязательной скамьи. Если набор не покрывает условия, добавить нужный вариант или явно сократить поддерживаемый профиль; количество 12 — ориентир, не цель любой ценой.
- [ ] Выбрать источник разрешённых текстов для русского рерайта; сохранить лицензию/авторство/изменения.
- [ ] Назначить проверяющего силовой методики и отдельно йоги.
- [ ] Проверить локальную среду Node/PostgreSQL/Docker или альтернативу; закрепить версии и lockfile.
- [ ] Завершить живой auth spike Яндекса/VK и Qwen spike на синтетических данных.

Готово: одна схема ресурсов/версий; понятный local boot и права; первые 12 карточек имеют план подготовки. Никакие draft не выдаются как утверждённая тренировка.

## 1. Каркас, БД и инвентарь

- [ ] Создать Next.js/React/TypeScript, общий validation/domain слой и CI.
- [ ] Подключить готовые PWA icons/manifest и metadata; две темы независимо от персонажа.
- [ ] Создать первые Drizzle/SQL migrations: auth principal, профиль, ресурсы/контексты, варианты/ревизии, медиа/права.
- [ ] Добавить идемпотентный draft importer с проверкой ID/FK, не массовую публикацию.
- [ ] Реализовать серверные сессии выбранного auth adapter; dev-профиль только закрытого local окружения.
- [ ] Реализовать inventory profile и AND/OR availability: одна/две гантели, конкретная машина/рукоять, опора, пространство, optional mat/block.

Готово: чистая БД поднимается миграциями; пользователь выбирает реальные ресурсы, API возвращает совместимые записи; A не читает данные B.

## 2. Публикация контента и первая программа

- [ ] Переработать разрешённые исходные описания в ясные русские карточки; хранить происхождение.
- [ ] Утвердить технику, ошибки, стороны, счетчик и разрешённые замены пилота.
- [ ] Проверить отдельно допуск профиля: опубликованный вариант с подходящим оборудованием не назначается начинающему без экспертно заданной применимости.
- [ ] Сгенерировать отдельные static изображения Макса/Лики, проверить и связать с ревизиями.
- [ ] Сделать минимальную админку draft/review/publish, проверку прав и immutable revision.
- [ ] Реализовать шаблон full body A/B и конкретные план/шаги; дозировки только из проверенной методики.
- [ ] Добавить онбординг, «Сегодня», карточки, выбор темы/персонажа.

Готово: подходящая опубликованная программа сохраняется; в ней нет draft, отсутствующего снаряда и чужой карточки; оба персонажа показывают тот же вариант.

## 3. SessionEngine и первый полный сценарий

- [ ] Создать основной экран напарника: лицо Макса/Лики, подготовленные реплики, карточка текущего действия и прогресс; затем подключить к нему Qwen.
- [ ] Реализовать start, record/correct set, rest, next/skip, finish и resume.
- [ ] Хранить snapshot версий, unit/laterality и server revision; один контракт для UI и AI.
- [ ] Добавить operation journal, idempotency и транзакционные XP/achievements/outbox.
- [ ] Показать историю результата, исправления и причину выбора/замены.
- [ ] Проверить потерю ответа, дубль команды, два устройства и ownership.

Готово: пользователь проходит online занятие; повтор не дублирует подход, завершение и награду.

## 4. Реальный офлайн PWA

- [ ] Выбрать/проверить SW-подход; кешировать оболочку и согласованные assets, не все private API.
- [ ] Создать Dexie schema, session state и partition по аккаунту.
- [ ] Добавить offline package с pinned revisions/assets/hashes и статусом полноты.
- [ ] Различать обычное retired и отзыв revoked; при следующем соединении заблокировать отозванную карточку и предложить утверждённую замену, сохранив историю фактических результатов.
- [ ] Добавить durable command queue, сверку результата, expiry auth и конфликт revisions.
- [ ] Проверить авиарежим, закрытие/возврат, нехватку места, очищенный кеш, обновление SW.
- [ ] Проверить на физическом Android и iPhone установку, таймер в фоне и повторный офлайн запуск.

Готово: загруженное занятие завершено без сети и затем принято один раз. Подготовленные реплики доступны, cloud chat явно offline.

## 5. Постоянный Qwen-напарник

- [ ] Сначала подготовить server product entitlement/capability map ADR-0004, bootstrap candidate и trial activation; paid AI не внедряется поверх проверки только replyLimit. Archive reads/account/export/delete и replay прежних операций проходят отдельные права.
- [ ] Подготовить persona/style contract по [социальной динамике](coach-social-dynamics.md): постоянный характер, transient просьбы, scoped confirmed preferences, optional initial hint; candidates не подтверждаются автоматически. Не добавлять обязательный gender questionnaire или вторую модель ради коллеги.
- [ ] Пройти парные coach/style [synthetic cases](../data/ai/evals/coach-style.v1.json): одинаковые бизнес-исходы, разные голоса, neutral address, stop/short, no jealousy, scope/reset/epochs и отсутствие ложных действий. Затем человеческая проверка естественности; fixtures не равны пройденным model-evals.
- [ ] Зафиксировать typed domain verdict и capability checks по [политике AI](ai-domain-policy.md); off-topic, mixed, clarify и safety не получают business tools.
- [ ] Подготовить короткие отказы Макса/Лики и provider-independent действие срочной помощи/утверждённый fallback; не расходовать квоту полезных ответов на отказы и технические ошибки, сохраняя ограничения частоты/provider budget.
- [ ] Проверить [шаблоны prompt](prompts/coach-domain-policy.v1.md) на development, затем на отложенной синтетике: тема, ограничения питания, приватность, инструментальные эффекты, память и списания. Разметка требует review; существующий набор не является пройденными evals.
- [ ] Реализовать server gateway, буферизованный model draft с output review до публичного SSE, компактный контекст и tool schemas. Все фазы входят в 4 calls / 4 tools / 20 секунд и общий input budget; исключить непроверенный fallback.
- [ ] Подключить рецепты/меню по [границам питания](ai-nutrition-boundaries.md); справки по добавкам требуют действующего проверенного материала и отдельных evals, а не свободного знания модели.
- [ ] Связать get state/record/correct/rest/next/finish/suggest swap с реальным SessionEngine.
- [ ] Добавить draft/confirm program update; права и условия проверяет сервер.
- [ ] Добавить один full-product trial 168 часов, server product entitlement, owner-scoped usage/spend/abuse guards и bounded AI-intent completion после expiry по [ADR-0004](adr/0004-product-subscription-and-archive-access.md); не старую квоту 150 реплик или отдельный AI-only paywall.
- [ ] Пройти сценарии русской речи, неоднозначности, timeout, боли, отказа и prompt injection.
- [ ] Измерить успешность, p50/p95 и расход целой сессии, а не один короткий ответ.

Готово: напарник ведёт ту же работающую тренировку, сообщает только исполненные действия и укладывается в измеренный бюджет. Цена/нормы после этих измерений.

## 6. Пуши, комплексы и расширение

- [ ] Утвердить короткие комплексы из [сценариев уведомлений](notification-scenarios.md).
- [ ] Добавить preferences, categories/consent, timezone/quiet hours, Web Push subscriptions.
- [ ] Реализовать outbox worker, планирование, cancellation, TTL, retries и semantic dedupe.
- [ ] Выбирать совместимый routine version сначала фильтрами, затем recent-aware вариативностью.
- [ ] Проверить отказ разрешения, stale settings/plan, позднюю доставку, expired endpoint.
- [ ] Доводить остальные варианты из CSV до публикации по покрытию профилей; йогу выпускать после собственной проверки последовательностей.

Готово: уведомление предлагает подходящий необязательный следующий шаг, открывает актуальную карточку, не раскрывает результат на lock screen и выключается настройками.

## 7. Тестовая подписка и допуск beta

- [ ] Внедрить product capability map до paywall: trial/paid active и archive-only независимо от account/security status. Архив, export/delete, account/billing/support остаются доступны.
- [ ] Внедрить атомарную однократную trial activation после onboarding/готового плана без SMS/карты; новые trial grants допускаются по бюджету beta до старта.
- [ ] Создать bounded session admission для одного заранее допущенного занятия; проверить expiry midworkout, late sync/XP, owner/snapshot/cutoff, revoked content и unknown/duplicate ACK до нового entitlement check.
- [ ] Ввести один план 299 ₽/календарный месяц, billing anchor и точную дату периода; убрать Free/Plus и нормы 1/4 адаптации. Состояния архивного UI используют подтверждённые данные, pending queue показана отдельно.
- [ ] Подключить test payments; проверить status/webhook, period grant, renew/cancel/refund.
- [ ] Проверить archive reads обоих чатов с прежними scope/epoch, отсутствие новых AI/compaction/training pushes после expiry и восстановление без backlog/потери истории/новой пробы.
- [ ] Измерить весь trial journey и paid usage; учесть пробы без покупки, C_trial/conversion, infrastructure/fees. До публикации закрепить честные нормы без скрытого budget cutoff.
- [ ] Настроить stage в РФ, logs без чувствительных payload, мониторинг, backup и restore.
- [ ] Подготовить основания обработки реальных данных, согласия, реестр прав и поддержку.
- [ ] Получить OAuth/API условия и credentials; live payment после бизнеса и договоров.
- [ ] Ограничить beta budget/партии по измеренным затратам; проверить вторую тренировку и возврат.

Готово: technical beta допущена по фактическим проверкам; live-оплата имеет отдельные условия. Импорт CSV, макеты и успешный тестовый webhook сами по себе этот допуск не подтверждают.

## Владение задачами

Ведущий агент владеет общими контрактами, миграциями и приёмкой. Sol — реализация ограниченного модуля; Luna — простые проверяемые операции; Cursor — отдельный UI/module slice по тем же контрактам. Файл/модуль в одном проходе имеет одного владельца. Независимый review перед интеграцией, затем связанный сценарий. Матрица и пример поручения — [roadmap](miron-roadmap.md#8-как-распределяем-работу-между-моделями-и-cursor).
