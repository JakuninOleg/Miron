# Вход в MIRON

Приложение использует Better Auth 1.7.7, PostgreSQL и Drizzle. Основной текущий вход — Яндекс ID; подключение VK отложено. Backend email/password сохранён и включается отдельной настройкой. SMS не подключён. При регистрации по email нужно подтвердить почту и войти. Пароль содержит от 10 до 128 символов; хеширование выполняет Better Auth.

`users.id` является единственным идентификатором пользователя. Служебные таблицы библиотеки: `auth_sessions`, `auth_accounts`, `auth_verifications`, `auth_rate_limits`. Схему создают миграции проекта, а не запросы браузера. Создание профиля и единственной пробы на 7 дней / 100 ответов выполняет серверный signup hook; повтор не создаёт новую пробу. Qwen пока не подключён.

## Локальный запуск

Установите зависимости проекта, запустите локальный PostgreSQL и примените миграции. Команды и порты описаны в README. Приложение открывается на `http://localhost:3000`. Для проверки email/password дополнительно запустите Mailpit: интерфейс на `http://localhost:8025`, SMTP на `127.0.0.1:1025`. Это локальный приёмник: письма не уходят внешним адресатам. Социальный вход не требует Mailpit или другого SMTP.

В `.env.local` должны быть `DATABASE_URL`, `BETTER_AUTH_URL=http://localhost:3000` и случайный `BETTER_AUTH_SECRET` длиной не меньше 32 символов. Локальное окружение содержит отдельный случайный секрет. Для почты по умолчанию используются Mailpit и отправитель `MIRON <hello@miron.local>`; их можно заменить `SMTP_HOST`, `SMTP_PORT`, `SMTP_FROM`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_SECURE`. Этот файл не коммитится. Никогда не добавляйте auth/SMTP/OAuth секреты в переменные `NEXT_PUBLIC_*`.

`AUTH_EMAIL_PASSWORD_ENABLED=false` включает режим входа только через настроенных социальных провайдеров: формы почты скрыты, SMTP transport не создаётся, HTTP endpoints регистрации/входа по email, восстановления, смены/установки пароля и подтверждения email отключены. Значение по умолчанию — `true`, чтобы сохранить прежний почтовый backend. Допустимы только `true` и `false`. `GET /api/auth/config` отражает этот флаг и доступность провайдеров без выдачи ключей. `requireEmailVerification=true` в публичной конфигурации относится к парольному входу.

Проверка email: зарегистрируйтесь на `/sign-up`, откройте письмо в Mailpit, перейдите по ссылке и войдите на `/sign-in`. Ссылка подтверждения действует 1 час. Восстановление: `/forgot-password`, письмо в Mailpit, `/reset-password`, новый пароль. Ссылка сброса действует 30 минут и погашается библиотекой; успешный сброс отзывает прежние сессии. Ответ API не содержит ссылку из письма. Неизвестный email не должен раскрывать существование аккаунта.

## Яндекс и VK

Вход OAuth отключён, пока оба значения соответствующего провайдера не заданы на сервере. `GET /api/auth/config` отдаёт только возможности входа. Незавершённая пара ключей приводит к отказу auth-конфигурации.

| Провайдер | Серверные переменные                       | Redirect URI в кабинете                          |
| --------- | ------------------------------------------ | ------------------------------------------------ |
| Яндекс ID | `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET` | `http://localhost:3000/api/auth/callback/yandex` |
| VK ID     | `VK_CLIENT_ID`, `VK_CLIENT_SECRET`         | `http://localhost:3000/api/auth/callback/vk`     |

Создайте отдельные приложения разработки в [Яндекс OAuth](https://oauth.yandex.ru/) и [VK ID](https://id.vk.ru/about/business/). У Яндекса запросите только `login:info` и `login:email`; у VK только `email`. Зарегистрируйте callback в точности, включая хост и порт. Production-приложения регистрируются отдельно с HTTPS callback своего домена. Не копируйте опубликованные примеры client secret.

11 октября создано отдельное приложение «MIRON — разработка» в Яндексе с этими двумя правами и локальным callback. Ключи записаны только в игнорируемый `.env.local`; настоящий вход проверен в Brave: обмен кода завершился, аккаунт и trial появились в PostgreSQL, открылась первая сцена `/onboarding`. VK отложен по решению пользователя, его ключи не настроены и кнопка неактивна. OAuth-приложение разработки не верифицировано Яндексом; эта локальная проверка не подтверждает production-домен или процедуру верификации.

Подключение VK отложено по решению пользователя 11 октября 2026. Кнопка VK ID остаётся неактивной, пока серверные ключи не заданы. Ранее доступ к кабинету VK ID был заблокирован политикой браузерного инструмента; обход ограничения не выполнялся. Реальный VK round trip ещё не проверен.

Яндекс подключён через Generic OAuth с `pkce: true`, authorization-code flow и заголовком `Authorization: OAuth` для получения профиля. Проверяются `client_id` ответа, стабильный числовой ID пользователя и формат контактного email. Получение профиля ограничено таймаутом, редиректы не разрешены, ответ не кешируется. [Документация PKCE Яндекса](https://yandex.ru/dev/id/doc/ru/codes/code-url) и [профиль Яндекс ID](https://yandex.ru/dev/id/doc/ru/user-information).

В установленной Better Auth 1.7.7 Generic OAuth регистрирует провайдера в общем social flow. Клиент вызывает `authClient.signIn.social({ provider: "yandex" })` через `/api/auth/sign-in/social`; прежние `genericOAuthClient` / `signIn.oauth2` в этой версии отсутствуют. Яндекс и VK используют общий callback `/api/auth/callback/:provider`. Клиент передаёт конечную страницу `/auth/continue`, которая продолжает путь реального аккаунта. Единственный дополнительный внутренний `next` — `/workout-builder`; произвольные адреса не принимаются. [Актуальная документация Generic OAuth](https://better-auth.com/docs/plugins/generic-oauth).

VK использует встроенный провайдер Better Auth: он передаёт PKCE verifier и callback `device_id` при обмене кода. Сетевой профиль отдельно проверяется приложением; для авторизации используется `user_id`. Запрашивается только scope `email`, стандартный scope `phone` отключён. [Настройка VK в Better Auth](https://better-auth.com/docs/authentication/vk), [реализация версии 1.7.7](https://github.com/better-auth/better-auth/blob/v1.7.7/packages/core/src/social-providers/vk.ts), [интеграция VK ID без SDK](https://id.vk.ru/about/business/go/docs/ru/vkid/latest/vk-id/connection/start-integration/auth-without-sdk/auth-without-sdk-web). Страница VK ID не была доступна инструменту чтения; HTTP flow сверён по установленной реализации библиотеки и изолированными тестами. Живой вход требует зарегистрированного приложения.

Социальный вход подтверждает личность по паре провайдер/стабильный subject и не отправляет письмо MIRON. Отсутствие `email_verified` не заменяется предположением: Яндекс/VK сохраняют `emailVerified=false`. Приватные API допускают такую сессию только при существующем связанном аккаунте Яндекса или VK, принадлежащем этому же `users.id`. Парольный аккаунт без подтверждённой почты доступа не получает. Автоматическое связывание отключено, в том числе при одинаковом email: чужой способ входа с совпадающей почтой получает `account_not_linked`. Изменение почты у уже связанного провайдера не меняет владельца аккаунта.

Если сервис не передал email, callback возвращает `email_not_found`, профиль и проба не создаются. Текущая схема Better Auth требует email; синтетический адрес или фиктивное подтверждение не используются. Для поддержки социальных аккаунтов без email потребуется отдельное решение по модели пользователя и восстановлению доступа.

Для дополнительных входов в РФ сначала разумно оценить Сбер ID: его официальная документация описывает вход для партнёров, но требует регистрации организации, оферты через ЭДО и сертификата. Это отдельная интеграция после первых email / Яндекс / VK сценариев. [Условия подключения Сбер ID](https://developers.sber.ru/docs/ru/sberid/guidebook/overview). Выбор основан на доступности интеграции; сравнительная популярность провайдеров не измерялась.

Другой кандидат — T-ID: у Т-Банка есть [публичная документация входа](https://developer.tbank.ru/docs/api/t-id) и [заявка подключения для бизнеса](https://www.tbank.ru/corporate/business-solutions/open-api/t-id/integration/). Сбер ID и T-ID пока не реализованы; их стоит добавлять по фактическому спросу пользователей после проверки договорных и технических условий.

## Серверные ограничения

Auth cookie имеет `HttpOnly`, `SameSite=Lax`, срок сессии 7 дней и `Secure` на HTTPS / в production. Cookie cache выключен. Приватные API вызывают `requireUser`: сессия читается на сервере, статус аккаунта и подтверждённая почта либо связанная социальная личность проверяются в PostgreSQL. Голосовой gateway использует ту же проверку; локальный анонимный preview не даёт обойти отказ авторизации уже вошедшего аккаунта. После удаления или блокировки аккаунта сохранённая cookie не даёт доступа. Провайдерские токены шифрует библиотека. У самой библиотеки session token хранится в служебной таблице; доступ к БД и backup должен быть ограничен.

POST auth допускается только с точным настроенным Origin и JSON до 16 KiB. Redirect callback, email verification и state/PKCE проверяет Better Auth. В OAuth state используется PostgreSQL и подписанная cookie. Укрупнённые ключи rate limit не содержат reset tokens; IP преобразуется HMAC перед записью guard-лимитера. Auth/API ответы не кешируются; service worker должен исключать auth и приватные API.

Guard rate limiter выполняет атомарный PostgreSQL UPSERT: 8 попыток в минуту на чувствительный endpoint, 100 для остальных. Он работает совместно с database limiter Better Auth и не теряет счётчик при параллельных экземплярах. По умолчанию forwarding headers игнорируются и запросы без доверенного IP разделяют общий bucket. Устанавливайте `AUTH_TRUST_PROXY=true` только за proxy, который удаляет входной `X-Forwarded-For` и записывает реальный IP первым. Не выставляйте Node-сервер напрямую в обход этого proxy. Устаревшие строки лимитера можно удалять плановым запросом, когда `last_request` старше суток; значение хранится в миллисекундах Unix time.

В production необходимы явные HTTPS `BETTER_AUTH_URL`, случайный `BETTER_AUTH_SECRET`, `DATABASE_URL` и ключи разрешённых социальных провайдеров. При включённом email/password обязательны полноценные SMTP настройки с пользователем/паролем и TLS; при `AUTH_EMAIL_PASSWORD_ENABLED=false` SMTP не требуется. Отсутствие нужной конфигурации или БД не включает запасной вход: клиент получает ошибку. SMTP отправитель, доставляемость, reverse proxy и восстановление backup проверяются отдельно перед публикацией. Ротация auth secret требует планирования: библиотека использует его для cookie, email verification и шифрования OAuth tokens. [Параметры Better Auth](https://better-auth.com/docs/reference/options).

## Проверки

11 октября прошёл набор из 41 изолированной проверки auth/config/policy/client и 18 проверок голосового gateway. Проверены отказ при неполных настройках, отсутствие секретов в публичной конфигурации, точный Origin, обработка forwarding headers, ограничения тела, серверное отключение email/password, принадлежность социальной личности и запрет доступа непроверенного парольного аккаунта. OAuth-тесты используют установленную библиотеку и memory adapter с подставными ответами провайдеров: проверяют state/PKCE, VK `device_id`, `emailVerified=false`, отсутствие почтового шага, стабильного владельца при изменении email, отказ связывания по совпавшей почте и отказ при отсутствии email. Это не живой вход в аккаунты провайдеров.

Ранее интеграционные тесты прошли на локальных PostgreSQL и Mailpit: регистрация, письмо подтверждения, вход, HttpOnly cookie, одинаковый ответ восстановления для известного и неизвестного email, одноразовый сброс, отзыв старой сессии, отклонение старого пароля и блокировка аккаунта. Конкурентный лимитер разрешил ровно 8 из 20 одновременных запросов и начал новое окно после истечения прежнего. При текущем изменении эти DB/SMTP suites не запускались.

Повторить изолированные проверки: `node node_modules/vitest/vitest.mjs run src/server/auth src/client/auth-client.test.ts src/server/voice/gateway.test.ts`. Интеграционные проверки включаются отдельно: `MIRON_AUTH_INTEGRATION_TESTS=1` и `AUTH_EMAIL_PASSWORD_ENABLED=true`, затем `node --env-file=.env.local node_modules/vitest/vitest.mjs run src/server/auth`. Перед этим запустите локальные PostgreSQL:55432 и Mailpit:1025/8025 и примените миграции. Тесты отказываются работать с другим адресом БД / SMTP и удаляют созданные ими аккаунты. В PowerShell переменные устанавливаются командами `$env:MIRON_AUTH_INTEGRATION_TESTS = '1'` и `$env:AUTH_EMAIL_PASSWORD_ENABLED = 'true'`.

Полный Yandex/VK round trip проверяется после выдачи реальных dev credentials; наличие конфигурации не означает подтверждённую работу провайдера. Production SMTP и HTTPS reverse proxy ещё не проходили сквозную проверку.

Живой Yandex round trip теперь проверен отдельно, как описано выше. Для пути аккаунта добавлен `MIRON_ACCOUNT_E2E=1 node node_modules/@playwright/test/cli.js test tests/e2e/account-journey-live.spec.ts`: временные локальные социальные личности и подписанные сессии, без внешней авторизации и без записи credentials в trace. Проверяются первое знакомство, серверное сохранение и повтор после потерянного ACK, возврат в дашборд, изоляция владельцев, отказ кешированного доступа после 403 и replay без сброса trial/результатов.
