# Черновая библиотека занятий MIRON

10 октября подключена отдельная runtime-библиотека `planner-library.ts`: 16 силовых структур и 14 цельных последовательностей йоги/растяжки/мобильности. Её собственные дозировки и подбор `planner-v1` описаны в [реализации](../../docs/workout-planner.md). Это явный редакционный allowlist поверх фактических допущенных карточек БД, а не публикация старого JSON или заявление профессиональной проверки.

`starter-drafts.v1.json` — исходные данные для следующей реализации подбора и самостоятельного конструктора. Решение, путь пользователя и формулы: [спецификация](../../docs/workout-drafts-and-duration.md).

После подготовки v1 выполнен [поиск готовых авторских программ и комплексов](../../docs/research/ready-workout-sources-2026-10-08.md): 20 записей по силовым, домашним, аэробным занятиям, калистенике, растяжке и йоге. Это отдельное исследование для следующей адаптации; найденные источники не приписываются уже созданным 18 черновикам. Поиск не меняет JSON и не подключает данные к приложению.

- 18 шаблонов занятий, 3 последовательности подготовки/завершения, 8 недельных схем.
- 300 предварительных профилей времени существующих вариантов упражнений.
- Состав, опыт, дозировки и диапазоны времени — редакционные AI-черновики; профессиональная проверка не проводилась.
- `runtimeConnected=false`: файл не импортируется действующим seed, не публикуется и не подключает API.

## Поля и использование

`timingProfiles` содержит профиль конкретного `variantId`: метрика, порядок сторон, допущение секунд на повтор, диапазон подготовки и смены стороны. Имена/метрики/стороны взяты из текущих карточек; время — собственное допущение с `estimateOrigin=editorial_assumption`. Наличие профиля времени не даёт допуска к навыковому/сложному движению.

`routines` содержит реальные назначения warmup/cooldown. `templates` содержит основные slots и ссылки на эти последовательности. Развернуть ссылки один раз; затем суммировать время всего порядка. `closingSeconds`, если есть, — дополнительное явно описанное спокойное завершение.

`slot.targetScope=total` означает общее число, `per_side` — на каждую сторону. У slot ровно одна цель по метрике: `targetReps` или `targetDurationSeconds`. `loadKg=null` — вес неизвестен; `loadPolicy=user_confirmed` требует отдельного подтверждения. Значения не выводятся из пола, массы тела, чужих записей или названия шаблона.

`requirementSources` переносит исходные выражения equipment/support/space конкретных упражнений, включая подготовку/завершение. Это исходные выражения каталога, а не новая грамматика ресурсов: назначения используют существующий разбор AND/OR/количества/опор. Контекст `home/gym/outdoor` не заменяет проверку инвентаря. Для офлайн-снимка нужны точные разрешённые ревизии и соответствующие медиа; строковый ID не является UUID ревизии.

`estimate` — вычисленный редакционный снимок по `durationPolicy.version=planning-v1`. При любой правке его нужно пересчитать. Приложение не должно доверять присланной клиентом сумме или использовать её как факт выполненной работы. Очередь к тренажёру в диапазон не включена.

`programs.cycle` продолжается через границу недели. Частота основных и дополнительных занятий раздельная. `partial_with_user_confirmation` — намерение будущего поведения, не существующая workout-команда. Пропуск не переносит двойную нагрузку; календарь и права доступа проверяет будущая интеграция.

`rewardRoleProposal` не является источником истины для XP. Серверу нужна единая классификация собственных и библиотечных занятий. Нельзя превращать черновики в `published` с заявлением о пройденной профессиональной проверке; продуктовая доступность и происхождение контента различаются.

Ссылки в `references` описывают общие основания; конкретные схемы и временные коэффициенты не приписываются этим публикациям. Источники самих карточек остаются в `data/catalog`, права и атрибуция не заменяются этим файлом.
